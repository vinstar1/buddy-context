# 版本管理规范 · Buddy 用量看板

> 一句话：**代码用 git tag 锁住，线上用产物 tag 锁住，业务用版本台账说清楚。**

本文由 `version-ledger` 技能生成，最后更新 2026-11-09。命令按 GitHub 写，若仓库迁到别的平台，只需改下面第 3 步和平台相关命令，其余不变。

## 一、先分清三本账

| 账本 | 记什么 | 存在哪 | 谁看 |
|---|---|---|---|
| 代码版本 | 这一版的完整源码 | git tag `v0.3.0`（本地 + `https://github.com/vinstar1/buddy-context`） | 开发 |
| 发布版本 | 线上跑的到底是哪一版 | 产物 tag（`app:0.3.0`）/ 部署配置里的版本变量 | 开发 / 运维 |
| 业务版本 | 为什么改、改了什么、什么时候 | `docs/versions.json` → `docs/version-board.html` | 业务 / 老板 |

三本账对得上，才不会出现「业务说第一版最好，你却找不回第一版」。

## 二、版本号怎么定

`主.次.修订`，0.x 是试用期：

- **修订位** `0.3.1`：0.3.0 承诺的行为不变，只是没做到或做错了（bug、错字、错位）
- **次位** `0.4.0`：行为或界面变了，哪怕只是挪一个按钮、加一个字段
- **主位** `1.0.0`：正式上线，或有不兼容改动（接口路径改了、老数据不能用了）

**判断标准不是改了多少行代码，是业务看到的东西变没变。**

一句话测试：把两版并排给业务同事看，**他能看出区别吗？**

| 他的反应 | 该用 |
|---|---|
| 「嗯，正常了」——之前是坏的，现在不坏了 | 修订位 `0.3.1` |
| 「咦，不一样了」——之前能用，现在换了样子或多了东西 | 次位 `0.4.0` |

版本号本身也是给老板的信号：`0.3.1` 是「上次那版有小毛病，修了」，`0.4.0` 是「按你们的意见做了一轮新的」。汇报时版本号先替你说话。

两件事可以同时成立：这轮反馈里如果有「按钮点不动」这种硬 bug，先发 `0.3.1` 修掉，再做 `0.4.0`。不用攒着。

0.x 阶段次位涨得快是正常的，`0.10.0` 之后是 `0.11.0`，不是 `1.0.0`。正式上线才进 1.0.0。

版本号**只写在 `VERSION` 一个地方**。应用启动时读它，健康检查接口把 `version` 返回出来——部署完先请求一次，就知道线上跑的是哪一版。

## 三、每次发版做这几件事

```bash
NEW=0.4.0    # 换成这一版要发的号

# 1. 开一个新版本（改 VERSION + 往台账插一条骨架 + 重生成看板）
python docs/version_ledger.py new $NEW "这一版的主题"

# 2. 写业务账：把业务原话和拆解填进 docs/versions.json
#    business  = 业务为什么要改（业务听得懂的话）
#    changes   = 按分组写，一条一句
python docs/version_ledger.py build          # 重生成看板，确认没写错

# 3. 提交 + 打标签（标签只在两个时刻打：给业务演示那天、上线那天）
git add -A
git commit -m "feat: v$NEW 这一版的主题"
git tag -a v$NEW -m "v$NEW 这一版的主题"
git push origin HEAD --tags

# 4. 在 GitHub 上留一份可检索的发布记录（可选但推荐）
python docs/version_ledger.py notes $NEW --out notes.md
gh release create v$NEW --title "v$NEW" --notes-file notes.md

# 5. 产物 / 数据快照（有数据库或镜像时）
#    镜像带版本号，不要只留 latest；数据库结构变了就存一份
mkdir -p _releases/v$NEW
docker build -t <应用>:$NEW . && docker tag <应用>:$NEW <应用>:latest
cp <数据文件> _releases/v$NEW/

# 6. 部署并确认版本
#    服务器 .env 写 APP_VERSION=$NEW（或等价的版本变量），再重启
curl -s <健康检查地址>     # 看到 version = $NEW 才算完
```

打产物 tag、存数据快照这两步的目的只有一个：**任何一版都能在 10 分钟内回到线上。**

## 四、三种回滚

| 场景 | 怎么做 | 影响 |
|---|---|---|
| 只想看看旧版长什么样 | `git checkout v0.3.0` | 只影响本地，不动线上 |
| 线上退回上一版 | 部署配置里把版本变量改回 `0.3.0`，重新部署 | 代码和界面回到旧版，数据保留 |
| 连数据一起回到那天 | 先备份当前库，再用 `_releases/v0.3.0/` 里的快照覆盖 | 会丢掉这之后的业务数据，谨慎 |

⚠️ **数据库只会向前迁移**（比如某版给表加了字段）。新代码配旧库会缺列直接报错；旧代码配新库一般能跑。所以**回滚代码前先看库是哪天的**，必要时连库一起回。

## 五、目录约定

```
<仓库根>/
├─ VERSION               版本号唯一来源（应用启动读它）
├─ docs/
│  ├─ versions.json               业务台账，唯一需要手写的文件
│  ├─ board-template.html         看板模板（改样式才动）
│  ├─ version_ledger.py           台账工具（init / new / build / check / notes）
│  ├─ VERSIONING.md               本文
│  └─ version-board.html          生成物，给老板看的那个
├─ _releases/v0.3.0/              数据快照、发布记录（不入 git）
└─ .gitignore
```

台账里每条版本只有 5 个必填字段：

```json
{
  "version": "0.3.0",
  "status": "demo",          // released 已交付 / demo 已演示 / iterating 开发中
  "theme": "这一版一句话主题",
  "business": "业务为什么要改，用业务听得懂的话写",
  "changes": { "用户端": ["..."], "管理端": ["..."], "后端": ["..."], "部署": ["..."] }
}
```

`date`（发布日期）、`feedback`（业务反馈原话）、`tag`（git 标签）、`note`（补充说明）按需补。

改动按「用户端 / 管理端 / 后端 / 部署」分组，一组一条一句，写「改成了什么」，不写「改了哪个文件」。

## 六、老板要看的时候

打开 `docs/version-board.html` → 点右上角「打印 / 导出 PDF」。

- **一页纸表格**：版本号、更新时间、业务需求、主要更新点、状态 —— 直接贴进汇报
- **逐版明细**：左边业务诉求、右边落地改动 —— 用来回答「为什么这么改」

## 七、给业务演示当天就要记

演示完当天，把业务同事的原话记进对应版本的 `feedback` 数组，哪怕只是「首页太花」「报告看不懂」这种半句话。

半年后有人说「第一版最好」，你翻到那一版的业务需求原文和当时记的反馈，就能把讨论拉回事实：**第一版好在哪、差在哪、当时为什么改。** 这比争论有用。

## 八、两条纪律

1. **不给业务看的版本不写台账，给了就要写。** 台账是给业务和老板看的，不是代码日记。
2. **`version-board.html` 是生成物，永远不要手改**，改 `versions.json` 再跑 `build`。

## 九、发版前自检

```bash
python docs/version_ledger.py check --remote
```

检查的是：台账字段是否齐全、`VERSION` 是否与台账最高版本一致、看板是否过期、标签是否本地和远端都有、台账改动是否已提交。全绿再发。
